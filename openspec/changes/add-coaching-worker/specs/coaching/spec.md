## ADDED Requirements

### Requirement: Scheduled coaching slots

The system SHALL run a standalone worker process that delivers a coaching message at three
fixed local-time slots each day — 07:00 (pagi), 13:00 (siang), 23:00 (malam). The worker
MUST sleep until the soonest future slot, run at that slot, then recompute the next slot.
The current slot MUST be derived from the local hour (before 12:00 → pagi, before 18:00 →
siang, otherwise malam), evaluated in the worker process's local timezone.

#### Scenario: Fire at a scheduled slot

- **WHEN** the worker's sleep elapses at a slot hour
- **THEN** it SHALL produce and deliver one coaching message for that slot
- **AND** compute and sleep until the next slot

#### Scenario: Roll over after the last slot

- **WHEN** the current time is after the last slot of the day (23:00)
- **THEN** the next run SHALL be scheduled for the first slot (07:00) of the following day

### Requirement: At-most-once delivery per slot

The system SHALL deliver at most one coaching message per slot per day, even across worker
restarts or double-fires. Before generating a message the worker MUST atomically claim a
per-day, per-slot key (`coaching:YYYY-MM-DD:slot`); it SHALL send only if it won the claim.

#### Scenario: Slot already sent today

- **WHEN** a run starts for a slot whose key has already been claimed today
- **THEN** the worker SHALL skip without sending and log that the slot was already sent

#### Scenario: First run for a slot

- **WHEN** a run starts for a slot whose key has not been claimed today
- **THEN** the worker SHALL win the claim and proceed to generate and deliver the message

### Requirement: State-grounded coaching message

Each coaching message SHALL be generated by an LLM from a prompt grounded in the user's live
state: the active mission, count of held missions, missions completed today, the 7-day
completion count, and scheduled habits that are due or missed today. The prompt MUST instruct
the model to be brief, to reference the supplied data without inventing figures, and to both
fire up motivation (semangat) and invoke fear of losing the dream (loss aversion). The message
MUST be delivered as Telegram HTML.

#### Scenario: Message reflects current data

- **WHEN** a coaching message is generated with no active mission
- **THEN** the prompt SHALL convey that there is no active mission
- **AND** the produced message SHALL be delivered to Telegram as HTML

### Requirement: Morning loss-aversion review

The 07:00 (pagi) slot SHALL use a distinct prompt that reviews the previous day's scheduled
habits — comparing the habits scheduled for yesterday's weekday against those logged within
yesterday's window — and highlights the missed ones as concrete loss plus exactly one
concrete improvement for today.

#### Scenario: Morning slot reviews yesterday

- **WHEN** the pagi slot runs
- **THEN** the prompt SHALL be the loss-aversion variant focused on yesterday's habits
- **AND** name yesterday's missed scheduled habits when any exist

### Requirement: Fallback when the LLM is unavailable

The system SHALL deliver a static, slot-specific coaching message when the LLM call fails for
any reason (missing key, error, timeout, empty response), so a message always lands instead of
nothing. The morning fallback MUST be grounded in yesterday's missed habits when available.

#### Scenario: LLM call fails

- **WHEN** generating the coaching text rejects
- **THEN** the worker SHALL log a warning and deliver the slot's static fallback message

### Requirement: Coaching worker resilience

The worker SHALL NOT crash when an individual run fails; per-run errors MUST be caught and
logged so the scheduling loop continues. A fatal startup error MUST exit the process with a
non-zero status code.

#### Scenario: A run fails

- **WHEN** a coaching run throws (e.g. database or delivery failure)
- **THEN** the error SHALL be caught and logged
- **AND** the worker SHALL continue scheduling subsequent slots
